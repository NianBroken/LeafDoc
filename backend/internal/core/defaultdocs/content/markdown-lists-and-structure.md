# 列表、引用与内容组织

列表适合把平行项目或连续动作分开，引用适合标明引文或独立提示。选择哪种结构，应根据读者如何使用内容来决定。必须按顺序执行的内容写成有序列表，可以独立完成的项目写成无序列表，需要记录完成状态的事项写成任务清单。

## 无序列表

行首使用短横线、加号或星号，后面留一个普通空格。同一组列表统一使用一种标记，避免源码看起来像多个不同层级。

```markdown
- 文档标题
- 适用对象
- 操作步骤
- 检查结果
```

显示结果：

- 文档标题
- 适用对象
- 操作步骤
- 检查结果

列表项应保持同一种语气，例如全部使用名词，或者全部使用动作句。不要让一项是“检查结果”，下一项却是一整段 无关 讨论。较长的解释应放在列表项下方，并按该项正文起点缩进。

## 有序列表

数字后接英文句点与空格表示有序列表。适合安装步骤、提交流程和排查顺序。阅读时浏览器会显示连续编号，但起始编号会影响第一项的显示。

```markdown
1. 打开目标页面。
2. 输入需要保存的内容。
3. 检查预览并保存。
4. 重新打开页面进行验证。
```

不要仅用数字列表罗列无先后关系的特点，否则读者会误以为必须依次完成。需要在中间插入步骤时，可以在源码里统一写 `1.`，渲染会生成顺序编号。用于审阅的文档也可以保留连续数字，方便原文核对。

## 嵌套列表

子项需要缩进到父项文字下面。为了跨编辑器保持清楚，常见写法是使用四个普通空格。不要混用制表符和全角空格。

```markdown
1. 上传文件。
    - 检查文件名。
    - 检查文件大小。
2. 验证访问。
    - 打开下载链接。
    - 确认文件内容完整。
```

嵌套层级越深，手机上留给正文的宽度越少。超过三级时应拆成小标题或独立段落，避免形成难以扫描的树状长列表。

## 列表中的第二段

同一项目需要多个段落时，在段落之间留空行，并让后续段落与该项目的正文起点对齐。没有缩进的段落会结束当前列表。

```markdown
1. 检查目标文件。

    文件必须是准备提交的最终版本。

2. 保存记录。

    保存后重新打开页面检查。
```

如果后面的文字意外变成代码，检查缩进是不是超过了当前列表需要的范围。列表语法与代码块都使用缩进，调整时应同时观察预览，而不是只看原文中空格整齐。

## 任务清单

无序列表标记后写方括号。空格表示待完成，字母 `x` 表示已完成。方括号前后的位置不能任意省略。

```markdown
- [x] 写好文档标题。
- [x] 检查代码示例。
- [ ] 点击全部内部链接。
- [ ] 保存并重新打开页面。
```

显示结果：

- [x] 写好文档标题。
- [x] 检查代码示例。
- [ ] 点击全部内部链接。
- [ ] 保存并重新打开页面。

阅读页面中的复选框用于显示状态，不能把它等同于已经保存的交互表单。变更状态后应通过编辑和保存确认结果。任务项目要能够明确判断完成与否，避免写成“进一步改善体验”这类没有终点的句子。

## 引用块

行首的大于号加空格表示引用。连续多行可以组成一个引用块，块内也能使用列表和文字格式。

```markdown
> 提交前请检查附件链接。
>
> - 链接必须指向正确文件。
> - 文件应能直接打开或下载。
```

显示结果：

> 提交前请检查附件链接。
>
> - 链接必须指向正确文件。
> - 文件应能直接打开或下载。

真正引用外部内容时，应在引用后写明来源链接和必要上下文。引用样式不会自动核实原文，也不会替作者承担准确性检查。

## 分隔线

单独一行的三个短横线、星号或下划线可以产生分隔线。上下都留空行，避免短横线被理解为上一行的标题下划线。分隔线用于切分明显不同的内容，不需要放在每个段落后面。

## 把长文拆成可以执行的部分

每个小节围绕一个目标展开，说明动作后紧接成功现象。出现失败分支时，写清错误现象和对应处理，不要把所有错误处理堆在文章末尾。复杂表格不适合表达长篇执行步骤，应改为有序列表。

## 排查结构错误

列表没有出现时，检查标记后的空格。任务框显示为文字时，检查 `- [ ]` 的空格是否完整。引用一直延续到后面时，在结束位置增加空行。缩进反复变化时，统一改为普通空格，再逐段观察预览。

列表和引用的通用规则见 [CommonMark 规范](https://spec.commonmark.org/)，任务清单扩展见 [GFM 规范](https://github.github.com/gfm/)。
