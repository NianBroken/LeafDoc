# 标题、文本格式与代码

阅读示例文件 `guide.md` 时，**必须保存的设置**需要在关闭前确认，*辅助说明*解释原因，~~旧入口~~表示已停用的位置。

## 标题与强调

标题在井号后留一个空格。一级标题标示文章主题，二级标题划分任务，三级标题解释具体步骤。不要依靠大量加粗模拟层次。

```markdown
# 运维手册
## 查看服务
### 检查入口
普通文字、**重点文字**、*强调文字*和 ~~不再采用的方案~~。
```

## 行内代码与代码块

文件名、命令和字段名放进行内代码，例如 `other/compose.yaml`。多行命令使用围栏代码块。语言名称提供给高亮器，不能代替运行环境说明。代码块只展示文本，不会自动执行其中的命令。

```bash
printf '%s\n' '检查服务状态'
```

复制代码前确认自己处于正确目录，并理解命令是否会删除数据。文档中的演示命令不会替你创建业务环境。

## 空行与特殊字符

同一段中的换行不等于开启新段落。不同任务之间插入空行，避免说明与代码连成一个难以阅读的段落。需要展示井号、星号等标记本身时，用反斜杠转义或包进行内代码。

写完后检查预览中的代码缩进、换行和强调范围。如果后续所有文字都被显示为代码，检查围栏是否闭合，起止反引号的数量是否匹配。

## 让强调具有明确含义

强调用于提示读者在执行动作时必须关注的内容，不应覆盖整段文字。把是否需要保存、是否会覆盖已有资料等关键判断放在动作旁边，读者便能在执行前看到。普通说明保持正常字重，附加解释采用短句，避免把加粗、斜体和删除线叠加到同一段里。删除线适合展示曾采用的入口已经停用，紧接着仍应写出当前有效的位置，不能让读者自行猜测替代方案。

文章中出现文件名、参数名和界面文字时，应让读者看得出它们分别代表什么。文件名采用行内代码，按钮名称使用正常中文引号，动作使用明确的动词。讲解编辑文件时先说明目标文件在哪里，再展示需要修改的那一小段内容。不要将整份无关配置贴进正文，让读者在数百行代码里查找唯一需要改动的字段。

## 保留代码原样与必要上下文

复制代码之前检查运行对象、当前目录、权限和输入资料。代码块中的空格、引号和换行属于内容的一部分，不能为了排版好看而随意替换。展示多条命令时，在命令外用正文解释每一步的目的。示例中的输出需要与输入分开，避免读者将输出文字一并复制执行。涉及删除或覆盖的例子，应在动作之前写清目标范围，并让读者有机会先核对目标。

代码块的语言标记服务于阅读和高亮，不会安装对应解释器，也不会授予执行权限。网页中能够显示一段命令，不代表当前设备具备执行条件。把前置条件写在示例之前，执行结果写在示例之后，便于读者判断自己是否到达预期状态。代码较长时优先拆成有独立意义的小段，但不要把必须连续执行的语句拆散到不同章节，导致上下文丢失。

## 核对显示与复制结果

预览时检查标题是否进入正确层次、强调是否只覆盖预期文字、代码是否完整闭合。对包含反引号的示例，可以使用数量更多的反引号包住外层内容，使内层围栏仍作为示例文字呈现。长行在屏幕上换行属于显示行为，不能据此认定源文件中已有换行。需要精确复制时，粘贴到临时文本中核对，再用于真实文件。

给同事交付一段代码说明时，应让对方能够回答三个问题：在哪里操作、输入什么、看到什么算完成。发现示例无法复现时，先核对版本、目录与必要参数，不要直接把失败归结为阅读者操作错误。保存文章后重新打开，检查引号、中文字符和反斜杠是否仍与原文一致。保留简短有效的示例，比堆放没有说明的大段代码更有维护价值。
