# LeafDoc Docker 打包与安装维护说明

## 设计目标与交付边界

LeafDoc 的发行目标是把当前源码编译为可以直接运行的 Linux 应用，同时将网关与安装所需资料封装为离线交付包。目标设备具备 Docker 引擎和 Compose 后，不需要另行安装 Go、Node、前端依赖、Python 或应用运行库。交付包不是 Docker 软件安装器，也不是仅包含配置文件的示例。包内 images.tar 保存应用镜像和 Caddy 镜像，安装入口使用 docker load 导入，不在目标机器编译源码。

当前正式名称和版本由 other/project.json 集中管理，初始值为 LeafDoc 和 1.0.0。正式镜像支持 linux/amd64，对应通常所说的 x64 处理器。外部 MySQL 是管理员明确选择的部署边界，不包含在安装包中。管理员需要提前创建数据库，并授予连接账号必要的建表、查询、写入、更新和删除权限。初始化会通过可回滚事务实际执行增查改删，探测数据不保留。数据库应采用项目当前支持的 MySQL 版本，不能使用其他数据库引擎替代。数据库网络地址必须从应用容器内部可达，容器内 localhost 指向容器自身，不能用它代指宿主机或其他服务器。

## 唯一打包入口

在项目根目录执行 node other/scripts/package.mjs。此文件是唯一发行实现，原有构建和发行别名调用同一入口，不维护第二套发行逻辑。测试、代码检查、运行管理与系统安装脚本并不执行发行构建，因此不属于重复打包入口。安装入口不能生成发行包，也不需要访问源码仓库。

脚本从自身位置向上定位项目，不依赖终端当前目录。开始执行后检查根目录 installers，目录不存在就创建，存在就清空内部文件和子目录。脚本拒绝将输出目录设置为符号链接或目录联接，避免清理其他位置。这个目录只适合存放可重新生成的产物，不得放入唯一副本、业务备份或个人文件。清理旧产物是每次打包的既定行为，不提供保留旧文件的隐含分支。

源码输入来自 Git 已跟踪文件以及未被忽略的新增文件，工作区尚未提交的修改也进入快照。密钥、环境文件、运行数据、编译输出、依赖目录和发行目录排除。项目新增必要源文件时必须保证其未被 Git 忽略，禁止将必要资源放入运行数据目录。源码文件逐一计算 SHA256，复制到系统临时目录后构建。构建期间再次扫描源码，如果有效源码发生变化，脚本明确失败，维护人员应等待编辑完成后重新执行。

脚本不会自行拉取远端或覆盖工作区。修改项目之前应按项目规则同步远端，打包时则以正在使用的工作区为准。自动拉取会改变正在发行的内容，还会对未提交修改造成干扰，因此与发行实现分离。打包清单记录每个源码文件的摘要及整份清单摘要，镜像 revision 标签使用同一来源摘要。维护人员能通过清单追溯产物内容，不能仅凭文件名更新判断源码已经更新。

## 构建与命名

多阶段 Dockerfile 先构建前端，再把同次生成的静态页面嵌入 Go 二进制。最终运行镜像只带程序、证书库和必要入口工具，不携带编译器或 node_modules。正式发行使用无构建层缓存模式，不能以旧 dist 或宿主旧二进制替代编译。依赖仍依据锁文件下载，下载缓存与旧业务编译结果是不同概念。

名称由项目名称、版本和实际执行时间构成。时间部分按年月日时分秒及两位百分秒拼接，例如 LeafDoc_1.0.0_2026081715013745.tar.gz。两位小数来自毫秒整数除以十后截断，不能把它描述成完整三位毫秒精度。时间采用打包设备当前本地时间，清单另记标准时间字符串以便跨时区核对。每个交付包内部含 release.env、compose.yaml、install.sh、manifest.json、README.md 和实际镜像归档，校验清单用于安装前发现损坏。

## 系统级安装与权限

在 Ubuntu 解压产物后执行 sudo sh install.sh install。安装默认要求 root，不提供用户目录安装方式。部署文件保存到 /opt/leafdoc，私有部署环境和 Caddyfile 保存到 /etc/leafdoc，应用持久数据保存在 /var/lib/leafdoc。Docker 服务及部署实例属于系统共享资源，不依赖某个用户的登录会话。应用容器使用镜像内专用非特权账号，安装入口动态读取该账号的编号并设置持久目录权限，不能假定所有镜像永远使用同一个数字账号。

数据目录同时承载文档资源和受限安装配置，因此必须整体备份并限制宿主访问权限。数据库记录位于外部 MySQL，需要独立备份。只复制应用镜像不能备份文档与数据库。安装配置包含数据库密码和会话密钥，不能提交到 Git，不能附加到公开问题报告，不能通过普通下载接口提供。容器退出后持久目录仍然存在，重建应用不能删除它。

系统级安装不意味着让全部应用进程使用 root，更不意味着把容器里的编译工具安装到宿主。镜像内部封装运行环境，宿主只管理 Docker 和系统部署资料。兼容性建立在宿主具有可运行 Linux x64 容器的内核和 Docker 条件上。Ubuntu 18.04、20.04、22.04 和更新版本的实际测试结果应分别登记，不能用一个 Ubuntu 容器启动成功证明全部宿主版本兼容。

## 首次初始化的工作流程

安装入口为新实例生成随机安装令牌，写入受限文件并在安装终端展示。管理员通过 HTTPS 页面填写令牌、数据库连接信息和管理员资料。引导服务在数据库设置读取和 Wiki 创建之前启动，因此全新设备没有数据库配置时不会直接运行正式业务。初始化状态接口和存活检查可以访问，业务接口返回尚未初始化，不能只依靠浏览器跳转来保护正式系统。

提交要求 JSON，请求有大小限制，令牌位于 JSON 请求体中并进行恒定时间比较，不放入 URL 或可被代理错误日志记录的自定义头。管理员密码至少八个字符，邮箱和必填数据库字段接受校验。数据库密码按输入原样保存，空白、引号和等号不进行环境文件展开。数据库 TLS 启用后验证服务器名称和证书，可使用系统 CA，也可输入 PEM 格式的自定义 CA，不能通过跳过验证解决证书错误。

验证复用真实 Wiki 构造过程，因此会访问实际数据库并准备真实结构和管理员。MySQL 建表包含隐式提交，失败后不能声称所有操作自动回滚，重试必须沿用既有的幂等结构和管理员规则。失败返回引导页，不写成功标记。数据库权限或网络错误需要先修正根因，再提交同一安装实例。已产生的外部数据库结构不会因为网页报错而自动删除。

成功时关闭初始化资源，清除管理员明文初始密码，将连接信息、会话密钥和完成状态写到同一份结构化记录。临时文件采用受限权限，写入并同步后原子替换正式文件，避免成功标记与配置分开保存。正式服务随后使用这份实例配置，环境变量不能悄悄替换它。安装完成后初始化写入口不再运行，安装令牌不能用于正式登录。

## 重启、升级和故障处理

停止使用 sudo sh /opt/leafdoc/manage.sh stop，启动使用 start，状态使用 status，日志使用 logs。升级时从新包执行 sudo sh install.sh upgrade，镜像版本更新而已有环境、证书和数据保留。升级前应备份文件和数据库，涉及数据库结构变化时还要评估旧程序是否能读取新结构，不能把镜像回退等同于数据库回滚。

普通 uninstall 只移除服务容器并保留数据。只有 purge --confirm-delete-instance 才删除宿主持久实例目录和网关卷，外部 MySQL 不会被删除。重新安装之前应明确是否需要新数据库，因为复用旧数据库会保留已有管理员与业务资料。数据库暂时离线、配置文件损坏或权限错误是运维故障，不能自动退回首次引导，也不能为恢复页面显示而覆盖原配置。

旧部署若没有安装记录，不能凭目录存在就认定已完成网页初始化。既有开发启动路径保留原环境配置方式；启用网页安装的实例应在隔离副本验证数据库和管理员后接管，维护人员不得直接把未知旧库当作全新空库。接管实施与测试结果需要明确记录，未实现的自动迁移不能写成已支持。

## 本机、局域网与公网

默认网关在集中端口提供安装实例 CA 签发的 HTTPS。证书工具随应用镜像封装，安装时自动提取宿主地址并生成包含全部地址的同一张证书，使不发送 SNI 的 IP 访问同样有效。本机可用 localhost，局域网使用宿主实际地址，访问设备需信任实例 CA，否则浏览器会提示证书不受信任。本地 CA 与服务器证书保存在 /etc/leafdoc/tls 中，公网自动证书保存在网关持久卷中，均不能在每次重启时重新生成。执行 sudo sh /opt/leafdoc/manage.sh ca 可导出到 /etc/leafdoc/local-ca.crt，再导入访问设备的信任库。网关不向自身信任库安装 CA，因为它只负责签发与提供证书，访问者信任由客户端管理。应用内部使用同源 API 和相对路径，不把 localhost 写死到浏览器请求。

公网全新安装可通过 LEAFDOC_DOMAIN 指定域名，网关生成域名站点配置并使用 Caddy 自动证书。服务器需要正确 DNS、开放的入口端口和证书签发条件。既有安装切换公网应维护 /etc/leafdoc/Caddyfile，再重启网关。代理目标为内部 app 服务，不把数据库暴露为公网端口。网关在应用切换到正式服务期间对短暂连接失败执行有限重试，避免启动切换产生瞬时网关错误。Caddy 保留上传与长连接支持，部署路径前缀由应用配置统一处理。

目前没有真实公网服务器和域名，因此真实公网连通和正式证书签发不能登记为已验证。可以使用受控测试域名和代理环境检验配置与转发行为，但测试证书不能替代正式签发证据。局域网访问也需要实际第二访问路径验证，不能只测试回环地址后宣称所有网络场景通过。

## 体积与长期维护

体积优化以多阶段构建、去除开发依赖、去除调试符号和外层压缩为主要手段。不得删除页面渲染资源、字体、图表、附件处理、修订、导入导出、备份恢复或其他现有能力。必须分别记录镜像体积和归档体积，避免把压缩文件大小当作实际解压或运行磁盘占用。新增功能需要新增运行库时，应同步修改运行镜像并做实际业务测试。

后续维护应保留单一版本来源、单一发行入口、最新源码快照、成功配置原子保存、服务端初始化门禁和实例持久化这些原则。更新工具链时维护固定镜像引用和锁文件，不通过忽略错误继续发行。发行失败不得留下成功命名的半成品，临时目录在退出路径回收。构建过程中不得编辑有效源码，维护文档和测试报告应在正式打包前完成。

## 验证要求与证据

每次维护至少执行后端测试、前端测试、结构检查、静态检查、正式打包、包校验、镜像导入、安装和业务运行。初始化测试覆盖空字段、无效令牌、错误密码、不可达数据库、权限不足、TLS 错误、保存失败和并发提交。成功后测试管理员登录、文档读写、附件、搜索、修订、导入导出、备份恢复与实例设置。其他实际存在的功能应由路由和功能登记表补齐，不得用少量冒烟测试代替完整功能证明。

验证还应覆盖重启、重建、升级和数据库故障，确认不会重复引导。源码更新检查要实际改变可观察源码并重新打包，再从新镜像验证变化，文件名和构建退出码不足以证明最新代码进入镜像。所有结果必须记录实际执行环境与命令，未执行项明确列出。正常流程中的错误和告警应定位修复，错误输入的预期拒绝应单独记录，不能关闭日志掩盖问题。

## 可选功能配置

邮件服务器、反向代理认证、指标、API 密钥管理和其他既有可选功能的运行参数保存在 /etc/leafdoc/application.env。文件采用环境变量赋值格式，只允许系统管理员读取，变量名称以应用帮助中列出的 LEAFDOC 参数为准。修改后使用 start 重新创建受配置影响的服务，不以仅重启旧容器代替环境更新。安装和升级不会清空这份私有文件。数据库与会话密钥仍由经过验证的安装记录决定，不能用可选环境配置绕过首次初始化或覆盖已完成的实例数据库。

## 本地证书维护

本地根证书默认有效期为三千六百五十天，服务器证书默认有效期为八百二十五天，两项参数集中保存在安装入口顶部。管理员应在到期前检查证书，使用包内 OpenSSL 更新服务器证书并保留原 CA 私钥与根证书，随后重启网关加载证书。更换主机地址时也应更新服务器证书中的地址列表，不能靠关闭证书校验恢复访问。直接删除整个 tls 目录会失去原信任关系，不能作为常规续期方法。公网证书由 Caddy 自动续期，仍需保持域名解析、挑战入口与证书存储可用。本地证书续期属于维护动作，当前安装入口不提供后台定时续期服务。
