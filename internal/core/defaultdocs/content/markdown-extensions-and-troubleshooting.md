# 扩展语法、兼容性与排错

Markdown 并不是单一编辑器的全部功能集合。基础语法之外，表格、任务列表、数学公式、图表和 HTML 都由不同扩展与渲染规则共同决定。写作时要区分可以跨平台使用的基础结构，以及只在当前项目验证过的能力。本文把这些差异转换成可直接执行的检查方法。

前四篇分别介绍[基础流程](/markdown-getting-started)、[文字与代码](/markdown-text-and-code)、[列表组织](/markdown-lists-and-structure)以及[链接资源](/markdown-links-images-and-tables)。本篇负责解释为什么相同原文在两个地方显示不同，以及出现问题后从哪里开始排查。

## 当前项目的实际能力

LeafDoc 前端通过 react-markdown 解析正文，使用 GFM 处理表格、删除线、任务列表和脚注。公式交给数学扩展和 KaTeX，代码高亮交给对应插件，Mermaid 围栏由图表组件处理。原始 HTML 先解析，再经过清理，最终显示受允许标签和属性共同约束。

后端的链接提取、摘要和搜索使用自己的 Markdown 解析流程。正文预览能显示一个扩展，不表示摘要必然完整复制该扩展的视觉效果。搜索用于定位文字内容，不应拿搜索摘要代替正文排版验证。遇到两处输出不同，应先确认它们承担的职责，再判断是否需要修复。

## HTML 与 Markdown 混用

简单 HTML 可以表达上下标、折叠信息和部分排版，但不应成为默认写作方式。纯 Markdown 更容易迁移，也更容易在原文里维护。HTML 块和 Markdown 块之间留空行，避免解析器把原本希望执行的 Markdown 当作 HTML 块里的普通文字。

```html
<details>
<summary>查看检查说明</summary>

这里放置检查条件。实际能保留的标签以当前预览为准。

</details>
```

HTML 安全清理会移除脚本、危险事件属性及不允许的内容。事件属性被移除属于正确行为，不能把恢复危险代码当作排版修复。内联样式只允许项目明确认可的规则，不要依赖任意定位、外部脚本或浏览器扩展才能显示的页面。

需要展示 HTML 原文时，把它放入 `html` 代码围栏。这样读者看见的是标签，而不是标签产生的效果。说明安全示例时也使用围栏，不把具有攻击含义的片段直接插入实际正文。不要让一篇教程改变站点的安全约束。

## 脚注和补充说明

脚注用方括号、尖号和标识建立引用，在文末使用相同标识加冒号给出说明。每个脚注标识应清楚且唯一。适合脚注的是不影响主要流程的补充资料，执行步骤中的前置条件应直接写在步骤附近，不能让读者翻到文末才发现必要限制。

```markdown
保存后还应重新打开页面检查。[^verify]

[^verify]: 重新打开可以同时检查持久化内容和最终显示结果。
```

保存后还应重新打开页面检查。[^verify]

[^verify]: 重新打开可以同时检查持久化内容和最终显示结果。

脚注编号由渲染器生成，不要手工写死显示编号。修改引用顺序后检查跳转和返回链接。跨平台导出时，目标解析器没有脚注扩展就会显示原始符号，需要把重要补充内容转成普通段落。

## Mermaid 图表

代码围栏语言写成 `mermaid` 可以请求图表渲染。图表适合展示流程、关系和状态变化，少量节点比一张充满细线的大图更容易理解。节点文字尽量简短，详细说明留在图下面。用引号包围中文标签，可以减少标点与语法关键字之间的冲突。

```mermaid
flowchart LR
    A["编写原文"] --> B["检查预览"]
    B --> C["保存页面"]
    C --> D["重新打开验证"]
```

图中四步形成顺序流程。需要修改时编辑原始围栏，而不是修改浏览器生成的图形。首次打开图表需要加载对应模块，失败时检查模块请求和控制台，不要反复刷新掩盖稳定复现的问题。复杂图表先保留两三个节点，确认基础语法后再逐段扩展。

图表文字应当在浅色与深色主题下都能看清，窄屏下检查缩放和滚动。仅依赖颜色表达状态会让部分读者无法区分，应在标签里同时写出状态名称。图表不能替代必要的文字流程，这样即使图形暂时无法加载，读者仍能理解操作。

## 标记、上下标和数学差异

项目支持的文字标记扩展应以实际预览为准。普通 Markdown 不保证 `==重点==`、`^上标^` 或自定义提示块在所有平台有效。写入这些语法前先检查当前预览，不支持时用粗体、HTML 上下标或普通引用块替代，不为文章引入整套无关扩展。

公式使用双美元符号。单美元内容保持普通文本，可以正常书写金额。数学命令与程序反斜线含义不同，复杂公式从最短表达式开始核对。跨平台迁移时检查定界符、宏支持和字体，不能只比较源文件字节是否相同。

## 转义、实体与 Unicode

反斜线转义适合显示 Markdown 标点。HTML 实体适合表示需要明确编码的字符，例如 `&lt;` 表示小于号，`&gt;` 表示大于号，`&amp;` 表示与号。实体在正文和代码块中的表现不同，代码块用于展示原文，不能期待它自动解码成最终字符。

```markdown
显示普通星号：\*文字\*
显示比较关系：a &lt; b
显示连接符：A &amp; B
```

Unicode 让中文和其他文字能够直接保存，但外形相近的字符不一定相同。全角空格、普通空格、不换行空格和零宽字符会影响代码、链接和搜索。复制资料后出现无法解释的断行或匹配失败，检查原字符，不要只凭外观判断。文件统一保存为 UTF-8，出现乱码应检查读取和写入编码，而不是重新手工拼接损坏的文字。

文件名中的中文可以使用，链接地址仍需要正确处理 URL 编码。不要对已经编码的地址重复编码，否则百分号会继续转换，目标就会变化。大小写在 Windows 文件系统与其他部署环境中的处理不同，附件和页面地址应保持实际大小写一致。

## 按现象定位问题

全文突然进入代码样式，检查没有结束的围栏和多出的缩进。列表层级错乱，检查标记后的空格、续行对齐和制表符。表格没有形成行列，检查分隔行、列数和未转义竖线。粗体未生效，检查标记是否成对并贴紧内容。公式显示原文，检查双美元边界和段落位置。

链接打不开时，先看目标地址，再看请求状态和访问权限。图片缺失时，检查资源是否存在、内容类型是否正确、部署前缀是否丢失。保存失败时，观察编辑器状态与接口响应，不要把当前输入还在屏幕上等同于已经保存。浏览器里看到旧图时，核对资源版本、缓存与实际请求地址。

把问题缩减到一个最小例子，只保留发生异常的标题、列表或围栏。每次改一个因素，记录预期与实际结果。确认原因后再把正确写法放回完整文档，这比随机切换多个设置更快，也能避免破坏本来正常的部分。

## 发布前的完整检查

内容检查关注事实、步骤、输入与结果。格式检查关注标题、段落、围栏和表格。资源检查关注链接、图片和附件。兼容检查关注浅色、深色、窄屏与子路径。保存检查关注重新打开和刷新后的实际内容。将这几个方面分别完成，才能证明文档能够被真实使用。

本文档的完成标准是能够说明某项语法来自基础能力还是扩展，能够复现并缩减一个格式问题，并能通过原文、预览、网络请求和保存结果确定原因。后续写作沿用同样的方法，保持示例准确、结构清楚和资源有效。
