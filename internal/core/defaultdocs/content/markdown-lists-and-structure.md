# 列表、引用与内容组织

一篇文档的可读性很大程度来自组织方式。步骤用有序列表，并列事项用无序列表，待办工作用任务列表，引用资料用引用块。选择格式之前先明确这些内容之间的关系，不要把所有段落都改成圆点列表。本篇讨论每种结构该如何写，以及容易混淆的缩进和空行。

需要复习段落规则时阅读[Markdown 入门与写作流程](/markdown-getting-started)，需要在步骤里放命令时参考[文本格式与代码表达](/markdown-text-and-code)。链接和附件另见[链接、图片与表格](/markdown-links-images-and-tables)。

## 无序列表表达并列关系

短横线、星号和加号都能打开无序列表。标记后留一个空格，再写正文。一个列表内保持同一种标记，有助于阅读原文和查找差异。无序列表不表示先后顺序，适合列出所需材料、功能范围和检查项目。

```markdown
- 页面有明确标题。
- 示例能够直接理解。
- 附件链接可以打开。
```

实际效果：

- 页面有明确标题。
- 示例能够直接理解。
- 附件链接可以打开。

如果第二项必须等第一项完成后才能做，就应使用有序列表。不要让读者从圆点的排列位置猜测操作顺序。每项尽量使用平行句式，例如都从动作开始，或者都写检查结果。列表项中的逗号和句号属于正文，保持一致即可，不影响语法。

## 有序列表表达执行步骤

数字后加英文句点和空格，可以建立有序列表。原文从 1 开始最直观，后续按顺序写数字，维护者直接看原文也能判断顺序。连续列表中渲染器通常负责显示递增编号，不能依赖每项手写数字表达特殊业务编号。

```markdown
1. 打开需要编辑的页面。
2. 修改内容并检查预览。
3. 保存后重新打开页面。
```

如果业务需要保留固定条款号，例如 2.3.1，应把条款号作为普通文字或标题的一部分，不要把它交给自动编号。需要重新开始一个列表时，使用明确的段落或标题分隔。只插入空行通常仍属于同一个列表，不能保证编号重启。

普通句子以数字和句点开头时也会触发列表语法。需要显示原始编号而不生成列表，可以转义句点。例如 `2026\. 年度记录` 显示普通文字。遇到意外编号时，检查段落开头的数字、英文标点和空格组合。

## 任务列表记录状态

任务列表在无序列表标记后添加方括号。中间一个空格表示未完成，小写 `x` 表示已完成。方括号后继续留空格，再写任务描述。LeafDoc 的预览负责展示状态，修改状态应以编辑源文为准，不把预览中的复选框当成独立任务管理系统。

```markdown
- [x] 明确页面用途。
- [ ] 核对附件与链接。
- [ ] 让另一位成员复核操作步骤。
```

- [x] 明确页面用途。
- [ ] 核对附件与链接。
- [ ] 让另一位成员复核操作步骤。

任务描述需要能够判断是否完成。例如核对附件与链接有明确动作，处理一下文档则没有完成标准。长期追踪责任人、期限和统计时，应采用适合的业务工具，Markdown 的任务框只保存文本状态，不自动发送提醒或分配权限。

## 嵌套列表与缩进

缩进决定项目是否属于上一级。简单无序列表可以统一使用四个普通空格缩进子项，避免混用制表符。较长编号的有序列表应让续行和子内容对齐到父项正文开始处，不能把四个空格当成所有情形下的固定答案。

```markdown
- 发布前检查
    - 内容检查
        - 标题准确
        - 示例完整
    - 资源检查
        - 图片清晰
        - 链接有效
```

嵌套层级说明真实从属关系。三级以内通常足以表达日常检查，过深层级会占用手机屏幕宽度。内容复杂到需要六七级列表时，应拆分小节或独立页面。不要使用缩进模拟任意页面布局，缩进在 Markdown 中不是纯装饰。

## 在列表中放段落和代码

一项内可以包含多段文字、引用和代码。后续内容要缩进到父项正文位置，并在不同块之间留空行。没有缩进的普通段落会脱离列表，接着出现的编号又会形成新的结构，读者看到的步骤关系就会改变。

````markdown
1. 准备文件。

   文件名应能说明用途，不使用仅有日期而没有主题的名称。

2. 检查文件。

   ```powershell
   Get-ChildItem -File
   ```

3. 记录检查结果。
````

这个例子中第二个步骤的代码属于第二项。复制到正文后，确认代码围栏和命令都保留对应缩进。紧凑列表的项目之间没有空行，松散列表项目间留空行，两者都有效。较长说明使用松散列表更容易扫读，不应为了节省屏幕高度去掉所有分隔。

## 引用块与嵌套引用

行首的大于号用于引用块，大于号后留一个空格。多段引用中，空白分隔行也写大于号，可以明确保留引用范围。引用适合展示来自其他资料的原文，也适合在操作说明中放置独立提示，但引用格式本身不证明内容真实。

```markdown
> 文档应当让读者知道下一步做什么。
>
> 检查结果也应写入说明。
```

> 文档应当让读者知道下一步做什么。
>
> 检查结果也应写入说明。

两个大于号形成嵌套引用，适合区分引用中的再次引用。不要为了生成更多边框而叠加层级。引用外继续写正文时留空行，避免懒惰续行规则把后面的说明也算入引用。

```markdown
> 维护记录中写道：
>
> > 每次操作后重新验证访问。
>
> 本次检查采用同样的方法。
```

## 提示信息与分割线

最稳妥的提示写法是普通引用块加粗标签，例如下面的注意。某些平台提供 `[!NOTE]` 等彩色提示语法，LeafDoc 没有因此自动获得同样显示能力。跨平台文档使用普通引用，不能假设一个看起来熟悉的扩展已经启用。

> **注意**：保存成功后再关闭编辑页面。上传附件以后，还要检查正文中的附件引用。

三个短横线或三个星号单独成行可以生成分割线。分割线上下留空行，可以减少与标题下划线及列表的歧义。分割线适合隔开性质不同的内容，不适合代替每一节的标题。文档开头的三个短横线还会参与元信息解析，不要随意在开头放置没有结束边界的分隔符。

```markdown
上半部分说明操作方法。

---

下半部分记录检查标准。
```

## 用结构完成一份检查单

写一份发布检查单时，先用二级标题区分准备、执行和验证，再用有序列表写实际步骤。每个阶段下列出并列条件，只有真实待办才用任务框。引用块只放需要单独提醒的限制。读者扫一眼标题就应知道流程，再看列表就能执行。

排查时从最小块开始。子项没有嵌套，检查行首空格。正文意外变成代码，检查是否多缩进了四个空格。引用范围过长，检查引用后是否留空行。任务框显示原文，检查短横线、空格、半角方括号和括号内字符。保持每次只改一个结构，查看预览变化后再继续，能够快速找到实际原因。

本篇完成标准是一份包含三级以内嵌套、列表内代码、两段引用和明确完成状态的检查单。格式必须反映内容关系，不能仅为了让页面看起来复杂而增加结构。
