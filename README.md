# LeafDoc

LeafDoc 是可以自行部署的在线文档系统。使用者通过浏览器建立目录、编写 Markdown、上传附件、查找内容和管理访问权限。它把文档组织成页面树，适合维护操作手册、项目说明、学习笔记和团队知识库。

当前项目由 Go 后端、React 前端、MySQL 和 HTTPS 网关组成。前端构建结果嵌入 Go 程序，正式运行不需要再启动 Vite。页面正文和页面关系保存在 MySQL，附件、头像、品牌图片及快照等资源由实例数据目录保存。它不是把一个 Markdown 文件夹直接发布成网站的静态生成器，也不是只靠挂载目录就能完整备份的文件型系统。

## 这个项目解决什么问题

散落在聊天记录和个人文件里的说明难以查找，也难以判断谁能修改。LeafDoc 将内容放在同一个可访问的站点中，以目录区分主题，以搜索定位页面，以账号角色区分阅读、编辑与管理。使用者不需要先提交 Git 才能改正文，保存后即可从浏览器读取。

例如，一个团队可以建立“部署手册”目录，在下面分别维护安装、升级和故障处理页面。安装页面引用升级页面，附件区保存操作需要的文件。调整目录或页面名称时，使用页面重构预览检查受影响链接，再执行修改。需要重复查看的页面可以加入收藏，需要突出显示的内容可以置顶。

这些作用来自当前的页面、链接、搜索、收藏、用户和附件实现。它不代表系统具备多人同时编辑合并、审批流、组织级单点登录协议或文档评论等能力，不能把未实现的功能当作选型依据。

## 实际功能与使用方式

### 页面、目录与编辑

登录后进入页面树，在相应位置创建页面或目录，输入标题和内容，再保存。页面支持复制、移动、删除、排序和页面类型转换。标题供人阅读，页面标识用于内部引用，路径用于在站点中定位内容，三者并非同一个值。

编辑区采用 CodeMirror。Markdown 阅读区支持标题、段落、列表、引用、表格、代码块、链接和图片，并接入数学公式与 Mermaid 图。HTML 内容经过渲染和清理规则处理，不应把任意脚本或任意 HTML 样式作为可用功能。系统内置帮助提供与当前渲染方式对应的示例。

页面保存并非只更新屏幕。后端写入页面记录后，还会更新相关搜索、链接、历史、标签与属性。排查“正文已经保存但搜索结果没有变化”时，需要同时检查搜索状态与日志，不能反复保存来替代定位原因。

### 查找、链接与整理

搜索服务以 MySQL 保存索引。输入关键词后由接口返回匹配内容，前端展示结果。后台重同步用于重新加载和整理相关索引状态，执行期间应观察任务状态和错误结果。

页面链接服务提供出链、反向链接和失效链接检查。一个页面引用了哪些内容、哪些内容又引用了它，均由链接关系帮助定位。页面重命名和移动应通过系统提供的操作进行，不能直接修改数据库记录来绕过这些关联处理。

标签与属性用于按正文中的元信息整理页面。收藏属于使用者的个人入口，置顶用于页面组织。它们服务于不同用途，不应把收藏理解为改变所有人的页面顺序。

### 附件与内容导入

附件通过系统上传接口保存，并由页面引用。图片与可下载文件都需要正确的资源地址，浏览器无法读取使用者电脑上的本地路径。删除、复制与恢复页面时，资源关系由对应业务流程处理。

导入功能采用“建立计划、检查计划、执行导入”的流程。先上传要导入的内容，再查看页面和资源的安排，确认后执行。代码包含嵌套目录、相对链接、README、附件和 Obsidian 风格链接的处理与测试。导入不是对任意格式文件都能保留全部表现的通用转换器，应先用一个小包检查结果，再导入完整资料。

### 账号、权限与站点设置

系统定义 `admin`、`editor` 和 `viewer` 三种角色。管理员负责用户及实例管理，编辑者负责内容维护，阅读者负责浏览。界面入口限制与后端接口鉴权共同生效，隐藏按钮不等于权限控制的全部。

公开访问开关决定未登录访问的阅读行为。公开阅读不授予编辑和管理权限。首次默认值与管理员后续保存的设置应当区分，重新设置启动环境变量不等于覆盖已经持久化的实例设置。

设置区包含账号、偏好、站点品牌、公开访问、目录显示、用户、API 密钥、快照、导入和失效链接等入口。入口是否显示还受角色及功能配置控制。API 密钥管理、历史和邮件流程应按实际启用状态理解。

启用 SMTP 后，系统提供找回密码、重置密码及邀请相关流程。前端在未启用 SMTP 或配置外部登录地址时不提供相同的本地邮件入口。外部代理认证需要配合受信任的代理配置，不能把客户端自行填写的请求头当作可靠身份。

### 历史、快照与恢复

页面历史记录与完整快照解决不同问题。历史用于查看页面版本；完整快照将数据库导出与附件、品牌、头像及历史资源组织成 ZIP，并记录校验信息。现有部署入口启用历史与快照，直接运行程序时仍须核对相应参数。

完整备份必须覆盖 MySQL 和实例文件资源。只保存 Docker 镜像不能保留业务数据；只复制实例数据目录也不能替代数据库备份。恢复前先备份当前实例，在隔离实例中验证归档后再处理正式数据。部署文档提供相应维护入口。

## 启动项目

### 选择部署路径

源码部署的 Compose 栈包括 MySQL、应用和 Caddy。离线发行包的栈只有应用和 Caddy，数据库在首次引导中配置。这两种模式的数据位置、配置入口和管理命令不同，不能混用。

准备 Ubuntu 主机时，需要 Git、Node.js、Python 3、OpenSSL、Docker Engine 和 Compose 插件。Node.js 用来调用仓库工具，Go 与前端依赖由 Linux 构建容器提供。版本以 `other/.nvmrc`、`backend/go.mod` 和各 Dockerfile 为准。

在已满足工具要求、具备 Docker 权限的 Ubuntu 主机上，源码部署入口如下：

```bash
git clone https://github.com/NianBroken/LeafDoc.git
cd LeafDoc
sudo bash other/scripts/deploy.sh init
node other/scripts/container.mjs build
sudo bash other/scripts/deploy.sh start
sudo bash other/scripts/deploy.sh status
```

`build` 会调用完整发行打包入口，不只是编译一个后端文件。它生成应用镜像和离线安装包，输出位于 `installers/`，并清理该目录内已有内容。需要保留旧发行包时，构建前将它复制到仓库之外。

初始化默认在 `/etc/leafdoc-compose` 保存私有配置和本地证书。启动脚本使用这些配置启动服务，并调用部署验证程序。部署时需要将访问主机名或地址加入证书配置，向客户端安装受信任根证书。完整步骤及公网域名模式见 Ubuntu 部署说明。

### 地址、端口和登录

项目的端口由 `backend/internal/core/serviceports/ports.json` 集中管理。当前 HTTPS 前端为 `24691`，后端为 `24692`，网关管理为 `24693`，指标为 `24694`。后端端口参数按共享分配校验，不支持随意改成其他值。

本机 HTTPS 入口是 `https://localhost:24691`。远程访问时将主机替换为实际服务器地址，并确保网关绑定、证书和防火墙允许访问。设置 URL 前缀后，访问路径需要包含相同前缀。

源码 Compose 初始化会生成管理员密码并写入私有环境配置，不要将代码中的初始密码当作该实例的实际密码。管理员初始化参数只在没有现有管理员时参与创建，不会在普通重启时重置已有账号。

离线安装通过安装令牌保护首次初始化。打开引导页后配置真实数据库连接和管理员资料，完成初始化才进入正式系统。已有数据库包含管理员时，流程会校验已有管理员凭据。没有通过健康检查、实际登录和页面访问，不能判定部署完成。

### 当前 Windows 电脑的启动入口

项目提供 `other/scripts/start.ps1`，使用 Docker Linux 容器运行应用，由宿主 Caddy 提供 HTTPS。脚本需要可用的 Docker、Node、Caddy、数据库及受信任的证书，私有配置从进程环境或 `other/.env` 读取。

```powershell
pwsh -File other/scripts/start.ps1 -Build
```

该入口与 Ubuntu Compose 的管理方式不同。脚本保存运行状态并将应用放入后台，不能用关闭终端是否退出判断运行是否正常。停止时使用同一脚本的 `-Stop` 参数。具体数据目录、证书路径与访问地址以脚本参数及输出为准。

## 架构与数据流

浏览器通过 HTTPS 访问 Caddy。Caddy 将请求转发给 Go HTTP 服务，后端提供嵌入的前端静态资源和 `/api` 接口。前端加载实例配置与登录状态后建立页面路由，再通过接口读取页面树、正文和设置。

后端按三层组织。HTTP 层处理请求、响应、认证上下文与静态资源；Wiki 层把具体功能组织成用例与路由；Core 层负责页面、账号、数据库、搜索、导入、历史及快照等底层业务。命令入口负责解析参数、初始化服务和管理生命周期。

一次保存的主要顺序是浏览器提交内容、后端验证权限和输入、页面服务写入数据库、保存编排器处理相关索引与历史、接口返回结果。搜索与链接属于围绕页面数据构建的关联信息，不能将前端显示缓存当作数据库中的最终状态。

数据保存分为两部分：MySQL 中的业务记录与搜索数据，实例目录中的文件资源和运行配置。源码 Compose 通过命名卷持久化数据库和应用资源；离线安装使用安装器定义的系统目录。容器可以替换，持久化数据必须保留。

## 接口如何参与运行

应用接口统一围绕 `/api` 组织，配置 URL 前缀后需要在它前面带上实例前缀。健康接口为 `/api/health`。页面、账号、搜索、附件、标签、属性、链接、历史、快照和导入均有对应路由。

浏览器登录采用服务端定义的会话与令牌机制。接口调用需要遵守各路由的认证与权限要求，读取权限不能推导出写入权限。上传文件、下载快照和流式状态的请求响应不同于普通 JSON，调用前查阅[接口参考](other/api.md)。

## 日常维护与排障

源码 Compose 使用以下入口观察状态，不要为排错先删除持久化卷：

```bash
sudo bash other/scripts/deploy.sh status
sudo bash other/scripts/deploy.sh logs
sudo bash other/scripts/deploy.sh config
```

无法打开网页时，按网关端口、证书、应用健康、数据库连接的顺序定位。证书错误应检查主机名和信任链，数据库错误应检查实际数据库地址与权限，容器内的 `localhost` 指向容器本身，不能用它代表宿主数据库。

能打开页面但不能登录时，核对账号来源、已有管理员状态、HTTPS Cookie、URL 前缀及外部认证配置。不要通过关闭安全检查或重置整库来代替处理。

升级前保存可恢复备份，保留旧发行包与私有配置。升级后检查健康、实际登录、页面、附件和搜索。容器重启策略只能在进程退出后按规则恢复容器，不会自动修好错误配置或损坏数据。完整维护步骤见部署文档。
